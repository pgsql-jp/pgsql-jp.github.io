5.7. Temporal Tables #

《機械翻訳》一時表を使用すると、ユーザは歴史のさまざまな次元を追跡できます。 アプリケーション時間は世界の物の歴史を追跡し、システム時間はデータベース自分自身の歴史を追跡します。 両方を行うデータベースはバイテンポラルとも呼ばれます。 このセクションでは、このような履歴を一時表で表現および管理する方法について説明します。

5.7.1. Application Time #

《機械翻訳》アプリケーション時間とは、表で記述された歴史のエンティティを指します。 通常の非時間テーブルでは、行ごとに1つのエンティティが存在します。 時間テーブルでは、エンティティにマルチプル行が存在する場合があります。 ただし、それらの行がその歴史からの重複しない期間を記述している必要があります。 アプリケーション時間では、各行にスタートと終了時間が存在し、行が適用される時期を表す必要があります。

《機械翻訳》次のSQLは、テーブル時間を格納できる一時的なアプリケーションを作成します。 

CREATE TABLE products (
    product_no integer,
    price numeric,
    valid_at daterange
);

《機械翻訳》一時的なテーブルのレコードは、図 5.1のようにタイムラインで想像することができます。 ここでは、2つの製品を記述する3つのレコードを示します。 各レコードは、製品番号、価格およびタプル時間の3つの属性を持つアプリケーションです。 製品5は、2020年1月1日から価格5.00で最初にオファーされましたが、2022年1月1日から8.00になりました。 2番目のレコードには終了時間の指定がなく、無期限または将来のすべての時間にわたって真であることを示しています。 最後のレコードは、製品6が2021年1月1日に9.00に導入され、2024年1月1日に取り消されたことを示しています。

図5.1 Application Time Example


《機械翻訳》テーブルでは、これらのレコードは次のようになります。 

 product_no | price |        valid_at
------------+-------+-------------------------
          5 |  5.00 | [2020-01-01,2022-01-01)
          5 |  8.00 | [2022-01-01,)
          6 |  9.00 | [2021-01-01,2024-01-01)

《機械翻訳》アプリケーション時間は単一のレンジ（タイプまたは複数範囲）として格納されるため、ここではカラム-レンジ表記を使用して表示します。 includeには始点を含めますが、終点は含めません。 このようにして、2つの隣接するカバー範囲のすべての点が重ならないようにします。 レンジタイプの詳細は、8.17を参照してください。

《機械翻訳》原則として、アプリケーション時間の範囲/マルチレンジを含むテーブルは、アプリケーション時間「インスタント」を格納するテーブルと同等です。 ミリ秒時間インスタントは、毎秒、最適化、ナノ秒、または使用可能な最も細かい粒度で1つずつ格納されます。 しかし、このようなテーブルにはあまりにも多くの行が含まれるため、範囲/マルチレンジは、コンパクトフォームで同じ情報を表すための拡張を提供します。 さらに、範囲とマルチレンジは、一般的な一時的な操作のためのより便利なインタフェースを提供します。 この場合、レコードの変更頻度が低いため、個別の「バージョン」がロータイム期間に存続します。

5.7.1.1. Temporal Primary Keys and Unique Constraints #

《機械翻訳》アプリケーション時間を含む表には、非一時コンセプトとは異なるエンティティ一意性のテーブルがあります。 一時エンティティ一意性は、一時主キーを使用して強制できます。 通常の主キーには少なくとも1つのカラムがあり、すべての列はNOT NULLで、すべての列の結合値はユニークです。 一時主キーにも少なくとも1つのそのようなカラムがありますが、さらに、最後のカラムがあります。 これは、行が適用される時期を示す範囲型またはマルチレンジタイプです。 キーの通常の部分は、どの時点でもユニークである必要がありますが、アプリケーション時間がオーバーラップしない場合は、ユニーク以外の行を使用できます。

《機械翻訳》一時的な構文を作成するための主キーは次のとおりです。 

CREATE TABLE products (
    product_no integer,
    price numeric,
    valid_at daterange,
    PRIMARY KEY (product_no, valid_at WITHOUT OVERLAPS)
);

《機械翻訳》この例では、product_noはキーの非一時パートであり、valid_atはレンジ時間を含むアプリケーションカラムである。

《機械翻訳》WITHOUT OVERLAPSカラムは暗黙的にNOT NULLです（キーの他の部分と同様）。 また、空の値、つまり'empty'のレンジまたは{}のマルチレンジを含めることはできません。 空のアプリケーション時間は意味がありません。

《機械翻訳》一意性制約ではない一時的な主キーを作成することもできます。 構文も同様です。 

CREATE TABLE products (
    product_no integer,
    price numeric,
    valid_at daterange,
    UNIQUE (product_no, valid_at WITHOUT OVERLAPS)
);

《機械翻訳》時間一意性制約では、アプリケーション時間に空の範囲/複数範囲を使用することも禁止されていますが、カラムはNULLであることが許可されています（一意性制約の他の列と同様）。

《機械翻訳》一時プライマリ・キーおよび一意制約は、B-Tree索引ではなくGiST索引（65.2）によってサポートされます。 実際には、一時主キーまたは一時制約を作成するには、btree_gist拡張機能をインストールして、データベースがキーの非一時部分用のGiST演算子クラスを持つようにする必要があります。

《機械翻訳》一時プライマリキーと一意性制約は、排他制約と同じ動作をします（5.5.6を参照）。 排他制約では、それぞれの正規キーパートが等しいかどうかで比較され、アプリケーション時間は例のオーバーラップと比較されますEXCLUDE USING gist (id WITH =, valid_at WITH &&).唯一の差は、空のアプリケーション時間も禁止されていることです。

5.7.1.2. Temporal Foreign Keys #

《機械翻訳》一時的な外部キーとは、あるアプリケーション時間のリファレンスから別のアプリケーション時間のテーブルまでのテーブルのことです。 一時的でないリファレンスが被参照キーの存在を必要とするのと同じように、一時的なリファレンスは被参照キーの存在を必要としますが、歴史の間はリファレンスが（少なくとも）存在します。 したがって、productsテーブルがvariantsテーブルによって被参照であり、製品5のバリアントのアプリケーション時間が[2020-01-01,2026-01-01)である場合、製品5はそのピリオド全体に存在する必要があります。

《機械翻訳》次のテーブルvariantsまだスキーマなしを使用して、外部キーを作成できます。 

CREATE TABLE variants (
  id         integer,
  product_no integer,
  name       text,
  valid_at   daterange,
  PRIMARY KEY (id, valid_at WITHOUT OVERLAPS)
);

《機械翻訳》ここでは、主キーの慣習として一時的なベストを含めていますが、外部キーでは厳密には必要ありません。

《機械翻訳》図 5.2は、同じ参照に対して、製品5（緑色）と2つのバリアント「タイムライン」（黄色）をプロットします。 バリアント8（中）が最初に導入され、次にバリアント9(XXL)が導入されました。 外部キー製品は制約全体に存在するため、どちらも被参照歴史を満たしています。

図5.2 Temporal Foreign Key Example


《機械翻訳》テーブルでは、これらのレコードは次のようになります。 

 id | product_no |  name  |        valid_at
----+------------+--------+-------------------------
  8 |          5 | Medium | [2021-01-01,2023-06-01)
  9 |          5 | XXL    | [2022-03-01,2024-06-01)

《機械翻訳》一時ノートは、被参照リファレンス内の単一行によって履行される必要はありません。 製品5は、バリアント8の歴史の途中で価格変更がありましたが、リファレンスはまだ有効です。 すべてのマッチング行の組合せを使用して、被参照歴史包含参照行かどうかをテストします。 テーブル

《機械翻訳》私たちの構文に一時的な外部キーを追加するテーブルは次のとおりです。 

CREATE TABLE variants (
  id         integer,
  product_no integer,
  name       text,
  valid_at   daterange,
  PRIMARY KEY (id, valid_at WITHOUT OVERLAPS),
  FOREIGN KEY (product_no, PERIOD valid_at) REFERENCES products (product_no, PERIOD valid_at)
);

《機械翻訳》ノート。 キーワードPERIODは、参照テーブルと被参照地域の両方で、アプリケーション時間のカラムに使用する必要があります。

《機械翻訳》仮主キーまたは一意性制約マッチング被参照列は被参照テーブルに存在する必要があります。

《機械翻訳》PostgreSQLはアクションNO ACTIONで一時外部キーをサポートしますが、RESTRICT、CASCADE、SET NULL、またはSET DEFAULTはサポートしません。

5.7.2. System Time #

《機械翻訳》システム時間は、それが記述する歴史ではなく、データベーステーブルのエンティティを参照します。 各行がいつ挿入/更新/削除されたかを取得します。

《機械翻訳》PostgreSQL現在はシステム時間をサポートしていませんが、トリガを使用してエミュレートすることができ、そのような機能を提供する外部拡張機能があります。
