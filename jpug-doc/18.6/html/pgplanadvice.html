F.30. 《機械翻訳》pg_plan_advice — プランナが正しいプランを取得するのを助ける #

《機械翻訳》pg_plan_adviceモジュールを使用すると、特別な目的の「キープランナ」ミニ言語を使用して、プランアドバイスの決定を記述、再現、および変更できます。 これは、ユーザが良いと信じるプランの選択を安定させるとともに、プランナが最適でないと信じる計画を実験することを目的としています。

《機械翻訳》ノートは、プランナが良い決定を下すことが多いため、その判断を覆すことは容易に裏目に出る可能性がある。 例では、基礎となるデータのディストリビューションが変化した場合、プランナは通常、良いパフォーマンスを維持するためにプランを調整するオプションを有する。 プランアドバイスがこれを防止する場合、非常に貧弱なプランが選択される可能性がある。 プランアドバイスを使用するのは、プランナの選択を制約するリスクが便益よりも上回る場合にのみ行うことが重要である。

F.30.1. さあ始めましょう #

《機械翻訳》最初に、pg_plan_adviceモジュールをロードに配置する必要があります。 これをシステム規模で実行するには、shared_preload_librariesにpg_plan_adviceを追加してサーバを再起動するか、session_preload_librariesに追加して新しいセッションを開始するか、またはLOADコマンドを使用して個々のセッションにロードします。

《機械翻訳》pg_plan_adviceモジュールが読み込まれると、EXPLAINはPLAN_ADVICEオプションをサポートします。 このオプションを使用すると、選択したプランのプランアドバイス文字列を表示できます。 例の場合:。 

EXPLAIN (COSTS OFF, PLAN_ADVICE)
        SELECT * FROM join_fact f JOIN join_dim d ON f.dim_id = d.id;
             QUERY PLAN
------------------------------------
 Hash Join
   Hash Cond: (f.dim_id = d.id)
   ->  Seq Scan on join_fact f
   ->  Hash
         ->  Seq Scan on join_dim d
 Generated Plan Advice:
   JOIN_ORDER(f d)
   HASH_JOIN(d)
   SEQ_SCAN(f d)
   NO_GATHER(f d)

《機械翻訳》この例では、ユーザは特定のアドバイスを指定していません。 その代わりに、プランナがmakeと考えるいかなる決定もベストに許可されており、それらの決定はアドバイス文字列のフォームで記念されています。 JOIN_ORDER(f d)は、fが駆動テーブルであり、それが結合される最初のテーブルがd.HASH_JOIN(d)はdハッシュ結合の内側に表示されることを意味します。 SEQ_SCAN(f d)はfとdの両方にシーケンシャルスキャンを介してアクセスされることを意味します。 NO_GATHER(f d)はfもdもGatherまたはGather Mergeノードの下に表示されないことを意味します。 プランアドバイスミニ言語の詳細については、以下のアドバイスターゲットおよびアドバイスタグに関する情報を参照してください。

《機械翻訳》問い合わせのアドバイス文字列を取得したら、それを使用して、その問い合わせがどのように計画されているかをコントロールに伝えることができます。 これを行うには、pg_plan_advice.advice選択したアドバイス文字列に設定します。 これは、システムによって生成されたアドバイス文字列、または自分で作成したにすることができます。 独自のアドバイス文字列を作成する良い方法の1つは、システムによって生成された文字列を取得し、強制したい要素だけを選択することです。 上記の例では、pg_plan_advice結合オーダー、結合メソッド、スキャンメソッド、および並列処理の使用のためにアドバイスを発行しますが、コントロール結合オーダーだけを発行することもできます:。 

SET pg_plan_advice.advice = 'JOIN_ORDER(f d)';
EXPLAIN (COSTS OFF)
        SELECT * FROM join_fact f JOIN join_dim d ON f.dim_id = d.id;
             QUERY PLAN
------------------------------------
 Hash Join
   Hash Cond: (f.dim_id = d.id)
   ->  Seq Scan on join_fact f
   ->  Hash
         ->  Seq Scan on join_dim d
 Supplied Plan Advice:
   JOIN_ORDER(f d) /* matched */

《機械翻訳》EXPLAINに対するオプションが指定されていないため、アドバイスに対してプラン文字列は生成されません。 ただし、提供されるプランアドバイスは引き続き表示されるため、EXPLAIN出力を見れば、選択されたプランがプランアドバイスの影響を受けていることがわかります。 提供されるプランアドバイスに関する情報が必要ない場合は、pg_plan_advice. always_explain_supplied_advice = false.提供されるアドバイスごとに、アドバイスが問い合わせに正常に適用されたかどうかを示すアドバイスフィードバックが出力に表示されます。 このケースでは、フィードバックに/* matched */と表示されます。 これは、fおよびdが問い合わせで検出され、検出された問い合わせプランが指定されたアドバイスに準拠していることを意味します。 PLAN_ADVICE

F.30.2. どうやって動くのか #

《機械翻訳》プランアドバイスは命令的に書かれています。 つまり、何をすべきかを指定しています。 しかし、実装レベルでは、pg_plan_advice何をすべきでないかをコアプランナに伝えることによって機能します。 言い換えれば、プランナの選択を制約することによって機能し、を置き換えることによって機能するのではありません。 したがって、アドバイスがどのようなを提供しても、コアプランナが問題の問い合わせに対して考慮したプランのみを取得できます。 アドバイス文字列を提供することによって正しいプランであると信じるものを強制しようとしたが、プランナが依然として目的のプランを生成できない場合、これはアドバイス文字列にバグがあるか、または問題のプランがコアプランナによって実行可能と見なされなかったことを意味します。 これは一般的に次の2つの理由のいずれかで発生します。 第1に、強制しようとしているプランが意味的に正しくない（つまり、間違いの結果を生成する）とプランナが信じているため、それが考慮されなかった可能性があります。 第2に、プランナがコスト以外の何らかの理由で、生成しようとしているプランを拒否した可能性があります。 例については、次のような非常に問い合わせの高いSELECT * FROM some_tableを前提とした場合、問い合わせーは、の使用がここでは役に立たないと判断し、原価計算計算を実行します。 enable_seqscan = falseを設定しても、このマップにを使用するように強制することはできません。 また、を使用するを使用するように強制することもできません。 問い合わせ前アドバイスインデックスシンプルプランナインデックスプランインデックス

《機械翻訳》プランアドバイスを指定しても、プランナ障害が発生することはありません。 ただし、不可能なことを要求するプランアドバイスを指定した場合、一部のプランがEXPLAINの出力でとしてフラグ付けされている計画ノードを取得する可能性があります。 場合によっては、このような計画は、提供されるプランがまったくない場合に取得したアドバイスと基本的に同じになりますが、他の場合には、はるかに悪い可能性があります。 例の場合:。 Disabled: true

F.30.3. 《機械翻訳》アドバイスの標的 #

《機械翻訳》アドバイスターゲットは、特定の問い合わせに含まれる特定のインスタンスの特定のリレーションを一意に識別します。 前述の例のようなシンプルの場合、アドバイスターゲットは単にリレーション別名です。 ただし、副問い合わせが使用される場合、表がパーティション化される場合、または同じリレーション別名が同じサブ問い合わせで2回以上言及される場合(foo JOIN bar ON foo.a = bar.a) x JOIN foo ON x.b = foo.bたとえば、は、より複雑な構文が必要になります。 これら3つの組合せは同時に発生する可能性があります。 リレーションは2回以上言及され、パーティション化され、サブ問い合わせ内で使用される可能性があります。

《機械翻訳》このため、リレーション識別子の一般的な構文は次のとおりです。 

alias_name#occurrence_number/partition_schema.partition_name@plan_name

《機械翻訳》alias_name以外のすべてのコンポーネントはオプショナルであり、必要な場合にのみ含まれます。 コンポーネントを省略する場合は、直前の句読点も省略する必要があります。 特定のサブ問い合わせ内でリレーションが初めて出現する場合、生成されたアドバイスでは出現番号が省略されますが、#1と記述することもできます。 テーブルパーティションの子の場合、パーティションスキーマとパーティション名前が必要ですが、それ以外の場合は両方とも省略されます。 プラン名前はトップ-レベルプランでは省略され、すべてのサブプランでは含める必要があります。

《機械翻訳》アドバイスを調べて正しい問い合わせターゲットを判断することは、必ずしも容易ではありません。 インスタンスの場合、プランナがサブ問い合わせを親問い合わせレベルにプルアップすると、その中にあるものはすべて親問い合わせレベルのパートになり、親問い合わせのサブプラン名前を使用します（トップレベルにプルアップされている場合はサブプラン名前は使用されません）。 さらに、正しいサブ問い合わせ名前が明確でない場合があります。 例の場合、2つの問い合わせーがUNIONまたはINTERSECTのようなオペレーションを使用して結合されている場合、サブ問い合わせー用の名前はSQL構文には存在しません。 代わりに、で生成された名前が各にアサインされます。 適切なターゲットを検出する最も簡単な方法は、を使用することですEXPLAIN (PLAN_ADVICE)そして、生成されたを調べます。 アドバイスシステムアドバイスブランチ

F.30.4. 《機械翻訳》アドバイスタグ #

《機械翻訳》アドバイスタグは、特定の結合問い合わせや結合オーダーなど、メソッドの一部に適用する必要がある特定の動作を指定します。 すべてのアドバイスタグは、アドバイスターゲットを引数として取り、多くのアドバイスターゲットのリストを許可します。 このリストは、場合によってはマルチプルレベルの深さまでネストできます。 アドバイスタグにはいくつかの異なるクラスが存在し、それぞれが問い合わせ計画の異なる側面を制御します。

F.30.4.1. 《機械翻訳》スキャンメソッドアドバイス #

SEQ_SCAN(target [ ... ])
TID_SCAN(target [ ... ])
INDEX_SCAN(target index_name [ ... ])
INDEX_ONLY_SCAN(target index_name [ ... ])
FOREIGN_JOIN((target [ ... ]) [ ... ])
BITMAP_HEAP_SCAN(target [ ... ])
DO_NOT_SCAN(target [ ... ])

《機械翻訳》SEQ_SCAN各ターゲットがSeq Scanを使用してスキャンされるように指定します.TID_SCAN各ターゲットがTID ScanまたはTID Range Scanを使用してスキャンされるように指定します.BITMAP_HEAP_SCAN各ターゲットがBitmap Heap Scanを使用してスキャンされるように指定します。

《機械翻訳》INDEX_SCANは、指定したターゲット名前でIndex Scanを使用して各インデックスをスキャンするように指定します。 INDEX_ONLY_SCANは似ていますが、ではIndex Only Scanを使用するように指定します。 どちらのケースでも、インデックス名前はスキーマで認定される可能性がありますが、必ずしもそうである必要はありません。

《機械翻訳》FOREIGN_JOINは、2つ以上の外部テーブル間の結合が、単一のForeign Scanとして実装できるように、ダウンをあるリモートサーバにプッシュする必要があることを指定します。 FOREIGN_JOINを単一の外部テーブルに対して指定することは必要でも許可されてもいません。 とにかくForeign Scanを使用する必要があります。 結合がダウンにプッシュされるのを防ぎたい場合は、その目的のためにJOIN_ORDERタグを使用することを検討してください。

《機械翻訳》DO_NOT_SCANは、特定のターゲットが最終プランにまったく表示されないように指定します。 ほとんどの場合、これは不可能であり、ターゲットリレーションのスキャンが使用不可とマークされるだけです。 ただし、場合によっては、プランナが最適化を検討し、計画ツリーの一部がコピーされて変化し、オリジナルの代替とみなされることがあります。 このような場合は、DO_NOT_SCANを使用して、優先されない代替を除外できます。

《機械翻訳》プランナは、ここに挙げた以外にも多くの種類のスキャンをサポートしています。 しかし、これらのほとんどの場合、意味のある決定を下すことができないため、アドバイスは必要ありません。 例では、FROM関数に現れる集合を返す句の出力は、Function Scanを使ってしかスキャンできないため、アドバイスが何かを変更することはありません。

F.30.4.2. 《機械翻訳》結合オーダーアドバイス #

JOIN_ORDER(join_order_item [ ... ])

where join_order_item is:

advice_target |
( join_order_item [ ... ] ) |
{ join_order_item [ ... ] }

《機械翻訳》サブリストなしでJOIN_ORDERが使用された場合、最初のアドバイス結合を駆動ターゲットとし、指定されたテーブル内で後続の各アドバイスターゲットに順に結合される、外側の深いオーダーを指定します。 インスタンスの場合、JOIN_ORDER(a b c)は、aが駆動テーブルであり、最初にbに、次にcに結合される必要があることを意味します。 問い合わせ内にa、bおよびcより多くのリレーションがある場合、残りは後で任意の方法で結合できます。

《機械翻訳》JOIN_ORDERリスト包含がカッコで囲まれたサブリストの場合は、外側の深い結合以外を指定します。 サブリスト内のリレーションは、サブリストがトップレベルJOIN_ORDERリストであるかのように、最初に互いに結合する必要があります。 次に、結果の結合製品は、結合オーダーの適切なポイントで結合の内側に表示される必要があります。 例の場合は、JOIN_ORDER(a (b c) d)このフォームのプランが必要です:。 

Join
  ->  Join
        -> Scan on a
        -> Join
             -> Scan on b
             -> Scan on c
  ->  Scan on d

《機械翻訳》中カッコで囲まれたJOIN_ORDERリスト包含aサブリストの場合も、深い結合の外側以外を指定しています。 ただし、サブリスト内の結合オーダーには制約はありません。 例の場合、JOIN_ORDER(a {b c} d)を指定すると、bおよびcのスキャンを以前の例でスワップできますが、カッコが使用されている場合はスワップできません。

《機械翻訳》括弧で括られたサブリストは任意にネストすることができますが、中括弧で囲まれたサブリスト自体はサブリストを含むことができません。

《機械翻訳》JOIN_ORDER()のマルチプルインスタンスは、オーダーオーダーを完全に制約するために、結合で必要になる場合があります。 これは、プランナによって個別に最適化されるマルチプル結合問題がある場合に発生します。 これは、副問い合わせが存在するため、またはパーティション化された結合があるために発生する可能性があります。 後者のケースでは、パーティション化された結合の各ブランチは、他のブランチから独立した独自の結合オーダーを持つことができます。

F.30.4.6. 《機械翻訳》パラレル問い合わせアドバイス #

GATHER(gather_item [ ... ])
GATHER_MERGE(gather_item [ ... ])
NO_GATHER(advice_target [ ... ])

where gather_item is:

{ advice_target |
( advice_target [ ... ] ) }

《機械翻訳》GATHERまたはGATHER_MERGEは、GatherまたはGather Mergeが、ターゲットとして指定された単一のリレーションのトップ、またはターゲットとして指定されたリレーションのトップの間の結合のリストにそれぞれ配置されることを指定します。 これは、GATHER(a b c)が3つの異なるGatherノードに対するリクエストであるのに対して、GATHER((a b c))は、3方向結合のトップ上の単一Gatherノードに対するリクエストであることを意味します。

《機械翻訳》NO_GATHERは、どのターゲットの上にもGatherまたはGather Mergeノードが表示されないように指定しますが、指定した結合問題の範囲内で計画が制約されるだけであり、親表または外側のサブ問い合わせレベルでもパラレル問い合わせを使用できます。 例に対して、NO_GATHER(inner_example@any_1)はParallel Seq Scanアクセスへの使用inner_exampleテーブルがany_1サブ問い合わせ内にあることは禁止されていますが、プランナがGatherまたはGather Mergeノードの下にSubPlan any_1を配置することは禁止されていません。 次のプランはNO_GATHER(inner_example@any_1)と互換性がありますが、NO_GATHER(outer_example)とは互換性がありません:。 

Finalize Aggregate
  ->  Gather
        ->  Partial Aggregate
              ->  Parallel Seq Scan on outer_example
                    Filter: (something = (hashed SubPlan any_1).col1)
                    SubPlan any_1
                      ->  Seq Scan on inner_example
                            Filter: (something_else > 100)

《機械翻訳》これは逆ケースです。 つまり、NO_GATHER(outer_example)とは互換性がありますが、NO_GATHER(inner_example@any_1):とは互換性がありません。 プラン 

Aggregate
  ->  Seq Scan on outer_example
        Filter: (something = (hashed SubPlan any_1).col1)
        SubPlan any_1
          ->  Gather
                -> Parallel Seq Scan on inner_example
                     Filter: (something_else > 100)

《機械翻訳》同様に、NO_GATHERが個々のパーティションに適用される場合、その特定のパラレルスキャンのパーティションは除外されますが、Parallel Appendノードがそのパラレルスキャンの非パーティションを使用することは可能です。 その可能性を排除するには、子ではなく親にNO_GATHERを使用します。

F.30.5. 《機械翻訳》アドバイスフィードバック #

《機械翻訳》EXPLAIN提供されるアドバイスが提供されるアドバイスごとにコメントのフォームの問い合わせに適用されたかどうかについてフィードバックに提供します。 例の場合:。 

SET pg_plan_advice.advice = 'hash_join(f g) join_order(f g) index_scan(f no_such_index)';
EXPLAIN (COSTS OFF)
    SELECT * FROM jo_fact f
    LEFT JOIN jo_dim1 d1 ON f.dim1_id = d1.id
    LEFT JOIN jo_dim2 d2 ON f.dim2_id = d2.id
    WHERE val1 = 1 AND val2 = 1;
                            QUERY PLAN
-------------------------------------------------------------------
 Hash Join
   Hash Cond: ((d1.id = f.dim1_id) AND (d2.id = f.dim2_id))
   ->  Nested Loop
         ->  Seq Scan on jo_dim2 d2
               Filter: (val2 = 1)
         ->  Materialize
               ->  Seq Scan on jo_dim1 d1
                     Filter: (val1 = 1)
   ->  Hash
         ->  Seq Scan on jo_fact f
 Supplied Plan Advice:
   INDEX_SCAN(f no_such_index) /* matched, inapplicable, failed */
   HASH_JOIN(f) /* matched */
   HASH_JOIN(g) /* not matched */
   JOIN_ORDER(f g) /* partially matched */

《機械翻訳》この問い合わせの場合、fは有効なアドバイスターゲットですが、gは有効ではありません。 したがって、fハッシュ結合の内側の設定するリクエストはmatchedと表示されますが、gハッシュ結合の内側の設定するリクエストはnot matchedと表示されます。 JOIN_ORDERアドバイスタグには、1つの有効ターゲットと1つの無効ターゲットが含まれるため、partially matched.ノートと表示されます。 HASH_JOIN(f g)は実際には2つの論理的に異なる動作のリクエストであるため、フィードバックではHASH_JOIN(f)とHASH_JOIN(g)に分解されます。 これに対し、JOIN_ORDER(f g)は単一リクエストであり、そのまま表示されます。

《機械翻訳》アドバイスフィードバックは、次のいずれかをincludeに載せることができます。

  • 《機械翻訳》matchedは、問い合わせの計画中に、指定されたすべてのアドバイスターゲットが同時に観測されたことを意味します。 このとき、アドバイスが実施される可能性があります。

  • 《機械翻訳》partially matched指定されたアドバイスターゲットのすべてではなく一部が、問い合わせー計画中に観察されたこと、またはすべてのアドバイスターゲットが観察されたが、同時には観察されなかったことを意味します。 例の場合、JOIN_ORDERアドバイスのすべてのターゲットが個別に問い合わせのマッチとなるが、提案された結合オーダーが合法でない場合に、これが発生する可能性があります。

  • 《機械翻訳》not matchedは、問い合わせの計画中に、指定されたアドバイスターゲットが観測されなかったことを意味します。 これは、単にアドバイスが問い合わせをマッチしない場合に発生する可能性があります。 または、問い合わせの関連部分が計画されなかった場合に発生する可能性があります。 これは、おそらく定数偽に単純化された状態によってゲートされたためです。

  • 《機械翻訳》inapplicable何らかの理由でアドバイスタグをアドバイスターゲットに適用できなかったことを意味します。 例の場合、存在しないインデックスを使用することが要求された場合、または、非セミジョインでコントロールセミジョインの一意性を維持しようとした場合に、このような状況が発生します。

  • 《機械翻訳》conflictingは、2つ以上のアドバイスリクエストの動作に互換性がないことを意味します。 例の場合、同じシーケンシャルスキャンに対してテーブルとインデックススキャンをアドバイスすると、両方の要求に競合を示すフラグが設定されます。 これは一般に、結合メソッドアドバイスまたはセミジョイン一意性アドバイスが、明示的に指定された結合オーダーと互換性がないことを意味する場合にも発生します。 F.30.4.3を参照してください。

  • 《機械翻訳》failedは、問い合わせプランがアドバイスに準拠していないことを意味します。 これは、matchedとしても示されているエントリでのみ発生します。 多くの場合、conflictingまたはinapplicableとしても示されているエントリで発生します。 ただし、pg_plan_adviceは判断できますが、アドバイスがプランナに準拠できる合法的なプランをコンストラクトに載せることができないという限りにおいて、アドバイスが有効である場合にも発生する可能性があります。 ノートにとって重要なのは、pg_plan_adviceによって実行される健全性チェックはかなり表面的であり、主にアドバイス文字列内のロジカルの不整合を探すことに重点が置かれています。 プランナだけが実際に機能することを知っています。

《機械翻訳》すべてのアドバイスは、matched、partially matched、またはnot matchedのいずれか1つとして正確にマークされる必要があります。

F.30.6. 設定パラメータ #

pg_plan_advice.advice (string)

《機械翻訳》pg_plan_advice.adviceは問い合わせ計画作成時に使用されるアドバイスの文字列です。

pg_plan_advice.always_explain_supplied_advice (boolean)

《機械翻訳》pg_plan_advice.always_explain_provided_adviceは、EXPLAINが常にすべての提供されるアドバイスと関連するアドバイスフィードバックを表示するようにします。 デフォルト値はtrueです。 falseに設定されている場合、この情報はEXPLAIN (PLAN_ADVICE)が使用されている場合にのみ表示されます。

pg_plan_advice.always_store_advice_details (boolean)

《機械翻訳》pg_plan_advice.always_store_advice_detailsにより、EXPLAINプラン問い合わせが使用されている場合でも、プリペアドアドバイスに関連する詳細を表示することができます。 デフォルト値はfalse.プリペアード問い合わせを計画するとき、EXPLAIN後で使用されるため、デフォルトによってオーバーヘッドを削減するために使用されるかどうかを知ることはできません。 pg_plan_advice提供されるアドバイスでプランアドバイスまたはフィードバックは生成されません。 これは、EXPLAIN EXECUTEプリペアード問い合わせで使用される場合、この情報を表示できないことを意味します。 この設定をtrueに変更すると、この問題は回避されますが、オーバーヘッドが追加されます。 このオプションをシステム全体ではなく、必要なセッションでのみ有効にすることは、おそらく良いアイディアです。

pg_plan_advice.feedback_warnings (boolean)

《機械翻訳》真が設定された場合、pg_plan_advice.feedback_warningsは、提供されるプランワーニングが正常に実施されなかった場合に必ずアドバイスを発します。 デフォルト値はfalse.

pg_plan_advice.trace_mask (boolean)

《機械翻訳》pg_plan_advice.trace_maskがtrue,の場合、pg_plan_adviceがpg_plan_advice回答で許容される問い合わせプラン型のマスクを提供されるプランアドバイスに変更するたびに、問い合わせ計画作成中にデフォルト値がメッセージを生成します。 はfalse.この設定で出力されるメッセージは、このモジュールをデバッグする目的以外に有用であるとは期待されません。 プリント

F.30.7. 制限事項 #

《機械翻訳》現在、集約に関するコントロールの動作のいかなる側面もプランナ化することはできません。 これには、集約が並べ替えまたはハッシュによって計算されるかどうか、および熱心な集約またはパーティションごとの集約などの戦略が使用されるかどうかの両方が含まれます。

《機械翻訳》また、現在のところ、UNIONやINTERSECTなどの集合演算に関するコントロールの動作のいかなる側面もプランナすることはできない。

《機械翻訳》仕組みで述べたように、プランアドバイスの利用は、プランナが存続可能と考えるプランの中からどのプランを選択するかに影響を及ぼすだけであり、プランナが検討を拒否した地域の選択を強制することは決してできない。

《機械翻訳》前のパラグラフで述べた制限の1つの結果は、GEQOが使われるとき、プランアドバイスは確率的にしか働かないということです。 提供されるアドバイスと互換性のある計画が存在したとしても、それらのどれかが候補のランダムに生成されたプールのパートになるという保証はありません。 そうでない場合、プランナは提供されるアドバイスに準拠しないプランを生成し、そのプランの一部は使用不可とマークされます。 結合計画をわずかしか制約しないアドバイスを提供した場合、GEQOは通常、それに準拠するプランを見つけることができます。 しかし、それをより実質的に制約したい場合は、満足な結果を得るためにオーダーでGEQOを無効にする必要があるかもしれません。 ノートスキャンアドバイスは結合オーダーを制約しないので、この制限の影響を受けません。

《機械翻訳》プランアドバイスは、問い合わせが計画されている場合にのみ参照されます。 あるプリペアドステートメントがpg_plan_advice.adviceの異なる値で、またはpg_stash_adviceなどの別のモジュールによって異なるアドバイス提供されるで再実行された場合でも、以前にキャッシュされたプランをmakeに使用できます。 PL/pgSQLブロック内でステートメントを再実行する場合も、同じことが発生する可能性があります。 この場合、プランもキャッシュできます。 以前にキャッシュされたプランを再利用しないセッションでは、DISCARD PLANSを使用できます。
