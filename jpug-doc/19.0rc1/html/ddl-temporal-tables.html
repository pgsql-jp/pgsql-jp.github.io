5.7. Temporal Tables #

<firstterm>Temporal tables</firstterm> allow users to track different dimensions of history. <firstterm>Application time</firstterm> tracks the history of a thing out in the world, and <firstterm>system time</firstterm> tracks the history of the database itself. (A database that does both is also called <firstterm>bitemporal</firstterm>.) This section describes how to express and manage such histories in temporal tables. 《機械翻訳》一時表を使用すると、ユーザは歴史のさまざまな次元を追跡できます。 アプリケーション時間は世界の物の歴史を追跡し、システム時間はデータベース自分自身の歴史を追跡します。 両方を行うデータベースはバイテンポラルとも呼ばれます。 このセクションでは、このような履歴を一時表で表現および管理する方法について説明します。

5.7.1. Application Time #

<firstterm>Application time</firstterm> refers to a history of the entity described by a table. In a typical non-temporal table, there is a single row for each entity. In a temporal table, an entity may have multiple rows, as long as those rows describe non-overlapping periods from its history. Application time requires each row to have a start and end time, expressing when the row is applicable. 《機械翻訳》アプリケーション時間とは、表で記述された歴史のエンティティを指します。 通常の非時間テーブルでは、行ごとに1つのエンティティが存在します。 時間テーブルでは、エンティティにマルチプル行が存在する場合があります。 ただし、それらの行がその歴史からの重複しない期間を記述している必要があります。 アプリケーション時間では、各行にスタートと終了時間が存在し、行が適用される時期を表す必要があります。

The following SQL creates a temporal table that can store application time: 《機械翻訳》次のSQLは、テーブル時間を格納できる一時的なアプリケーションを作成します。 

CREATE TABLE products (
    product_no integer,
    price numeric,
    valid_at daterange
);

Records in a temporal table can be imagined on a timeline, as in <xref linkend="temporal-entities-figure"/>. Here we show three records describing two products. Each record is a tuple with three attributes: the product number, the price, and the application time. So product 5 was first offered for a price of 5.00 starting January 1, 2020, but then became 8.00 starting January 1, 2022. Its second record has no specified end time, indicating that it is true indefinitely, or for all future time. The last record shows that product 6 was introduced January 1, 2021 for 9.00, then canceled January 1, 2024. 《機械翻訳》一時的なテーブルのレコードは、図 5.1のようにタイムラインで想像することができます。 ここでは、2つの製品を記述する3つのレコードを示します。 各レコードは、製品番号、価格およびタプル時間の3つの属性を持つアプリケーションです。 製品5は、2020年1月1日から価格5.00で最初にオファーされましたが、2022年1月1日から8.00になりました。 2番目のレコードには終了時間の指定がなく、無期限または将来のすべての時間にわたって真であることを示しています。 最後のレコードは、製品6が2021年1月1日に9.00に導入され、2024年1月1日に取り消されたことを示しています。

図5.1 Application Time Example


In a table, these records would be: 《機械翻訳》テーブルでは、これらのレコードは次のようになります。 

 product_no | price |        valid_at
------------+-------+-------------------------
          5 |  5.00 | [2020-01-01,2022-01-01)
          5 |  8.00 | [2022-01-01,)
          6 |  9.00 | [2021-01-01,2024-01-01)

We show the application time using range-type notation, because it is stored as a single column (either a range or multirange). Ranges include their start point but exclude their end point. That way two adjacent ranges cover all points without overlapping. See <xref linkend="rangetypes"/> for more information about range types. 《機械翻訳》アプリケーション時間は単一のレンジ（タイプまたは複数範囲）として格納されるため、ここではカラム-レンジ表記を使用して表示します。 includeには始点を含めますが、終点は含めません。 このようにして、2つの隣接するカバー範囲のすべての点が重ならないようにします。 レンジタイプの詳細は、8.17を参照してください。

In principle, a table with application-time ranges/multiranges is equivalent to a table that stores application-time <quote>instants</quote>: one for each second, millisecond, nanosecond, or whatever finest granularity is available. But such a table would contain far too many rows, so ranges/multiranges offer an optimization to represent the same information in a compact form. In addition, ranges and multiranges offer a more convenient interface for typical temporal operations, where records change infrequently enough that separate <quote>versions</quote> persist for extended periods of time. 《機械翻訳》原則として、アプリケーション時間の範囲/マルチレンジを含むテーブルは、アプリケーション時間「インスタント」を格納するテーブルと同等です。 ミリ秒時間インスタントは、毎秒、最適化、ナノ秒、または使用可能な最も細かい粒度で1つずつ格納されます。 しかし、このようなテーブルにはあまりにも多くの行が含まれるため、範囲/マルチレンジは、コンパクトフォームで同じ情報を表すための拡張を提供します。 さらに、範囲とマルチレンジは、一般的な一時的な操作のためのより便利なインタフェースを提供します。 この場合、レコードの変更頻度が低いため、個別の「バージョン」がロータイム期間に存続します。

5.7.1.1. Temporal Primary Keys and Unique Constraints #

A table with application time has a different concept of entity uniqueness than a non-temporal table. Temporal entity uniqueness can be enforced with a temporal primary key. A regular primary key has at least one column, all columns are <literal>NOT NULL</literal>, and the combined value of all columns is unique. A temporal primary key also has at least one such column, but in addition it has a final column that is of a range type or multirange type that shows when the row is applicable. The regular parts of the key must be unique for any moment in time, but non-unique rows are allowed if their application time does not overlap. 《機械翻訳》アプリケーション時間を含む表には、非一時コンセプトとは異なるエンティティ一意性のテーブルがあります。 一時エンティティ一意性は、一時主キーを使用して強制できます。 通常の主キーには少なくとも1つのカラムがあり、すべての列はNOT NULLで、すべての列の結合値はユニークです。 一時主キーにも少なくとも1つのそのようなカラムがありますが、さらに、最後のカラムがあります。 これは、行が適用される時期を示す範囲型またはマルチレンジタイプです。 キーの通常の部分は、どの時点でもユニークである必要がありますが、アプリケーション時間がオーバーラップしない場合は、ユニーク以外の行を使用できます。

The syntax to create a temporal primary key is as follows: 《機械翻訳》一時的な構文を作成するための主キーは次のとおりです。 

CREATE TABLE products (
    product_no integer,
    price numeric,
    valid_at daterange,
    PRIMARY KEY (product_no, valid_at WITHOUT OVERLAPS)
);

In this example, <literal>product_no</literal> is the non-temporal part of the key, and <literal>valid_at</literal> is a range column containing the application time. 《機械翻訳》この例では、product_noはキーの非一時パートであり、valid_atはレンジ時間を含むアプリケーションカラムである。

The <literal>WITHOUT OVERLAPS</literal> column is implicitly <literal>NOT NULL</literal> (like the other parts of the key). In addition it may not contain empty values, that is, a range of <literal>'empty'</literal> or a multirange of <literal>{}</literal>. An empty application time would have no meaning. 《機械翻訳》WITHOUT OVERLAPSカラムは暗黙的にNOT NULLです（キーの他の部分と同様）。 また、空の値、つまり'empty'のレンジまたは{}のマルチレンジを含めることはできません。 空のアプリケーション時間は意味がありません。

It is also possible to create a temporal unique constraint that is not a primary key. The syntax is similar: 《機械翻訳》一意性制約ではない一時的な主キーを作成することもできます。 構文も同様です。 

CREATE TABLE products (
    product_no integer,
    price numeric,
    valid_at daterange,
    UNIQUE (product_no, valid_at WITHOUT OVERLAPS)
);

Temporal unique constraints also forbid empty ranges/multiranges for their application time, but that column is permitted to be null (like the other columns of the unique constraint). 《機械翻訳》時間一意性制約では、アプリケーション時間に空の範囲/複数範囲を使用することも禁止されていますが、カラムはNULLであることが許可されています（一意性制約の他の列と同様）。

Temporal primary keys and unique constraints are backed by GiST indexes (see <xref linkend="gist"/>) rather than B-Tree indexes. In practice, creating a temporal primary key or constraint requires installing the <xref linkend="btree-gist"/> extension, so that the database has GiST operator classes for the non-temporal parts of the key. 《機械翻訳》一時プライマリ・キーおよび一意制約は、B-Tree索引ではなくGiST索引（65.2）によってサポートされます。 実際には、一時主キーまたは一時制約を作成するには、btree_gist拡張機能をインストールして、データベースがキーの非一時部分用のGiST演算子クラスを持つようにする必要があります。

Temporal primary keys and unique constraints have the same behavior as exclusion constraints (see <xref linkend="ddl-constraints-exclusion"/>), where each regular key part is compared with equality, and the application time is compared with overlaps, for example <literal>EXCLUDE USING gist (id WITH =, valid_at WITH &amp;&amp;)</literal>. The only difference is that they also forbid an empty application time. 《機械翻訳》一時プライマリキーと一意性制約は、排他制約と同じ動作をします（5.5.6を参照）。 排他制約では、それぞれの正規キーパートが等しいかどうかで比較され、アプリケーション時間は例のオーバーラップと比較されますEXCLUDE USING gist (id WITH =, valid_at WITH &&).唯一の差は、空のアプリケーション時間も禁止されていることです。

5.7.1.2. Temporal Foreign Keys #

A temporal foreign key is a reference from one application-time table to another application-time table. Just as a non-temporal reference requires a referenced key to exist, so a temporal reference requires a referenced key to exist, but during whatever history the reference exists (at least). So if the <literal>products</literal> table is referenced by a <literal>variants</literal> table, and a variant of product 5 has an application-time of <literal>[2020-01-01,2026-01-01)</literal>, then product 5 must exist throughout that period. 《機械翻訳》一時的な外部キーとは、あるアプリケーション時間のリファレンスから別のアプリケーション時間のテーブルまでのテーブルのことです。 一時的でないリファレンスが被参照キーの存在を必要とするのと同じように、一時的なリファレンスは被参照キーの存在を必要としますが、歴史の間はリファレンスが（少なくとも）存在します。 したがって、productsテーブルがvariantsテーブルによって被参照であり、製品5のバリアントのアプリケーション時間が[2020-01-01,2026-01-01)である場合、製品5はそのピリオド全体に存在する必要があります。

We can create the <literal>variants</literal> table with the following schema (without a foreign key yet): 《機械翻訳》次のテーブルvariantsまだスキーマなしを使用して、外部キーを作成できます。 

CREATE TABLE variants (
  id         integer,
  product_no integer,
  name       text,
  valid_at   daterange,
  PRIMARY KEY (id, valid_at WITHOUT OVERLAPS)
);

We have included a temporal primary key as a best practice, but it is not strictly required by foreign keys. 《機械翻訳》ここでは、主キーの慣習として一時的なベストを含めていますが、外部キーでは厳密には必要ありません。

<xref linkend="temporal-references-figure"/> plots product 5 (in green) and two variants referencing it (in yellow) on the same timeline. Variant 8 (Medium) was introduced first, then variant 9 (XXL). Both satisfy the foreign key constraint, because the referenced product exists throughout their entire history. 《機械翻訳》図 5.2は、同じ参照に対して、製品5（緑色）と2つのバリアント「タイムライン」（黄色）をプロットします。 バリアント8（中）が最初に導入され、次にバリアント9(XXL)が導入されました。 外部キー製品は制約全体に存在するため、どちらも被参照歴史を満たしています。

図5.2 Temporal Foreign Key Example


In a table, these records would be: 《機械翻訳》テーブルでは、これらのレコードは次のようになります。 

 id | product_no |  name  |        valid_at
----+------------+--------+-------------------------
  8 |          5 | Medium | [2021-01-01,2023-06-01)
  9 |          5 | XXL    | [2022-03-01,2024-06-01)

Note that a temporal reference need not be fulfilled by a single row in the referenced table. Product 5 had a price change in the middle of variant 8's history, but the reference is still valid. The combination of all matching rows is used to test whether the referenced history contains the referencing row. 《機械翻訳》一時ノートは、被参照リファレンス内の単一行によって履行される必要はありません。 製品5は、バリアント8の歴史の途中で価格変更がありましたが、リファレンスはまだ有効です。 すべてのマッチング行の組合せを使用して、被参照歴史包含参照行かどうかをテストします。 テーブル

The syntax to add a temporal foreign key to our table is: 《機械翻訳》私たちの構文に一時的な外部キーを追加するテーブルは次のとおりです。 

CREATE TABLE variants (
  id         integer,
  product_no integer,
  name       text,
  valid_at   daterange,
  PRIMARY KEY (id, valid_at WITHOUT OVERLAPS),
  FOREIGN KEY (product_no, PERIOD valid_at) REFERENCES products (product_no, PERIOD valid_at)
);

Note that the keyword <literal>PERIOD</literal> must be used for the application-time column in both the referencing and referenced table. 《機械翻訳》ノート。 キーワードPERIODは、参照テーブルと被参照地域の両方で、アプリケーション時間のカラムに使用する必要があります。

A temporal primary key or unique constraint matching the referenced columns must exist on the referenced table. 《機械翻訳》仮主キーまたは一意性制約マッチング被参照列は被参照テーブルに存在する必要があります。

<productname>PostgreSQL</productname> supports temporal foreign keys with action <literal>NO ACTION</literal>, but not <literal>RESTRICT</literal>, <literal>CASCADE</literal>, <literal>SET NULL</literal>, or <literal>SET DEFAULT</literal>. 《機械翻訳》PostgreSQLはアクションNO ACTIONで一時外部キーをサポートしますが、RESTRICT、CASCADE、SET NULL、またはSET DEFAULTはサポートしません。

5.7.2. System Time #

<firstterm>System time</firstterm> refers to the history of the database table, not the entity it describes. It captures when each row was inserted/updated/deleted. 《機械翻訳》システム時間は、それが記述する歴史ではなく、データベーステーブルのエンティティを参照します。 各行がいつ挿入/更新/削除されたかを取得します。

<productname>PostgreSQL</productname> does not currently support system time, but it could be emulated using triggers, and there are external extensions that provide such functionality. 《機械翻訳》PostgreSQL現在はシステム時間をサポートしていませんが、トリガを使用してエミュレートすることができ、そのような機能を提供する外部拡張機能があります。
