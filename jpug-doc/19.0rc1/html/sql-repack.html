REPACK

REPACK — rewrite a table to reclaim disk space

概要

REPACK [ ( option [, ...] ) ] [ table_and_columns [ USING INDEX [ index_name ] ] ]
REPACK [ ( option [, ...] ) ] USING INDEX

where option can be one of:

    VERBOSE [ boolean ]
    ANALYZE [ boolean ]
    CONCURRENTLY [ boolean ]

and table_and_columns is:

    table_name [ ( column_name [, ...] ) ]

説明

<title>Description</title>

<command>REPACK</command> reclaims storage occupied by dead tuples. Unlike <command>VACUUM</command>, it does so by rewriting the entire contents of the table specified by <replaceable class="parameter">table_name</replaceable> into a new disk file with no extra space (except for the space guaranteed by the <literal>fillfactor</literal> storage parameter), allowing unused space to be returned to the operating system. 《機械翻訳》REPACKは、無効なタプルによって占有されたストレージを回収します。 VACUUMとは異なり、table_nameで指定された名前の内容全体を、余分なディスクファイルのない新しいスペースに書き換えることによって行われます（fillfactorストレージパラメータによって保証されたスペースを除き、未使用のスペースをオペレーティングシステムに戻すことができます）。

Without a <replaceable class="parameter">table_name</replaceable>, <command>REPACK</command> processes every table and materialized view in the current database that the current user has the <literal>MAINTAIN</literal> privilege on. This form of <command>REPACK</command> cannot be executed inside a transaction block. Also, this form is not allowed if the <literal>CONCURRENTLY</literal> option is used. 《機械翻訳》table_nameがない場合、REPACKは、現在データベースにMAINTAIN権限があるすべてのテーブルおよびマテリアライズドビューを処理します。 REPACKのこのフォームは、トランザクションブロック内では実行できません。 また、CONCURRENTLYオプションが使用されている場合、このフォームは許可されません。

If a <literal>USING INDEX</literal> clause is specified, the rows are physically reordered based on information from an index. Please see <xref linkend="sql-repack-notes-on-clustering"/> below. 《機械翻訳》USING INDEX句を指定すると、インデックスからの情報に基づいて、行が物理的に並べ替えられます。 下記のNotes on Clusteringを参照してください。

When a table is being repacked, an <literal>ACCESS EXCLUSIVE</literal> lock is acquired on it, unless the <literal>CONCURRENTLY</literal> option is given. See <xref linkend="sql-repack-notes-on-concurrently"/> for a discussion on the effects of this option. 《機械翻訳》テーブルを再パックする場合、ACCESS EXCLUSIVEオプションが指定されていなければ、そのテーブルに対してCONCURRENTLYロックが獲得されます。 このオプションの影響についてはNotes on Concurrent Operationを参照してください。

パラメータ

<title>Parameters</title>

The name (possibly schema-qualified) of a table. 《機械翻訳》テーブルの名前です（スキーマ修飾名も可）。

column_name

The name of a specific column to analyze. Defaults to all columns. If a column list is specific, <literal>ANALYZE</literal> must also be specified. 《機械翻訳》特定のカラムからANALYZEまでの名前。 デフォルトはすべての列です。 カラムリストが特定の場合は、ANALYZEも指定する必要があります。

index_name

The name of an index. 《機械翻訳》インデックスの名前です。

CONCURRENTLY

Allow other transactions to use the table while it is being repacked. See <xref linkend="sql-repack-notes-on-concurrently" /> for more details. 《機械翻訳》再パック中に、他のトランザクションがテーブルを使用できるようにします。 詳細は、Notes on Concurrent Operationを参照してください。

VERBOSE

Prints a progress report as each table is repacked at <literal>INFO</literal> level. 《機械翻訳》各レポートがINFOテーブルで再梱包されるときに、進行レベルを印刷します。

ANALYZE
ANALYSE

Applies <xref linkend="sql-analyze"/> on the table after repacking. This is currently only supported when a single (non-partitioned) table is specified. This option cannot be used inside a transaction block, or from a function, procedure, or <command>DO</command> block. 《機械翻訳》再梱包後にテーブルにANALYZEを適用します。 これは現在、単一の（パーティション化されていない）テーブルが指定されている場合にのみサポートされています。 このオプションは、トランザクションブロック内では使用できません。 また、関数、プロシージャ、またはDOブロックからは使用できません。

boolean

Specifies whether the selected option should be turned on or off. You can write <literal>TRUE</literal>, <literal>ON</literal>, or <literal>1</literal> to enable the option, and <literal>FALSE</literal>, <literal>OFF</literal>, or <literal>0</literal> to disable it. The <replaceable class="parameter">boolean</replaceable> value can also be omitted, in which case <literal>TRUE</literal> is assumed. 《機械翻訳》選択したオプションをオンにするか、オフにするかを指定します。 TRUE、ON、または1と記述するとオプションが有効になり、FALSE、OFF、または0と記述すると無効になります。 ブールの値を省略することもでき、その場合はケースTRUEが想定されます。

注釈

<title>Notes</title>

To repack a table, one must have the <literal>MAINTAIN</literal> privilege on the table. 《機械翻訳》テーブルを再梱包するには、テーブルにMAINTAIN権限が必要です。

<command>REPACK</command> is primarily meant to remove bloat and, with <literal>USING INDEX</literal>, to cluster the table, in order to improve performance. Although it also advances the table's <structfield>relfrozenxid</structfield> and <structfield>relminmxid</structfield>, it is not a good way to prevent transaction ID or multixact ID wraparound: it rewrites the whole table and all of its indexes, so it takes much longer than <command>VACUUM</command>, and it can fail after most of the work is done, especially with <literal>CONCURRENTLY</literal> on a busy table. <command>VACUUM</command> is recommended for that instead (see <xref linkend="vacuum-for-wraparound"/>). When a table gets close to wraparound, <command>VACUUM</command> skips index vacuuming on its own (see <xref linkend="guc-vacuum-failsafe-age"/>), and its <link linkend="sql-vacuum"><literal>INDEX_CLEANUP OFF</literal></link> option can do the same earlier. 《機械翻訳》REPACKは、主に膨張を除去することを目的としており、USING INDEXとともにテーブルのクラスタまで、オーダーではパフォーマンスの改善までです。 テーブルのrelfrozenxidとrelminmxidも進みますが、トランザクションIDやマルチトランザクションIDの周回を防ぐのには適していません。 これは、テーブル全体とそのインデックスのすべてを書き換えるため、VACUUMよりもはるかに時間がかかり、特にCONCURRENTLYビジーテーブルで使用する場合は失敗する可能性があります。 VACUUM代わりに推奨します（24.1.5を参照）。 テーブルがクローズから周回に移動する場合、VACUUMはインデックスバキューム処理を自動的にスキップします（vacuum_failsafe_ageを参照）。 INDEX_CLEANUP OFFオプションを使用すると、同じことをより早く行うことができます。

<command>REPACK</command> refuses to process a table on which an invalid index exists. Such indexes must be dropped or reindexed by the user ahead of time. 《機械翻訳》REPACK無効なプロセスが存在するテーブルのインデックスを拒否します。 このようなインデックスは、事前にユーザによって削除または再インデックスされる必要があります。

While <command>REPACK</command> is running, the <xref linkend="guc-search-path"/> is temporarily changed to <literal>pg_catalog, pg_temp</literal>. 《機械翻訳》REPACKの実行中は、search_pathが一時的にpg_catalog, pg_tempに変更されます。

Each backend running <command>REPACK</command> will report its progress in the <structname>pg_stat_progress_repack</structname> view. See <xref linkend="repack-progress-reporting"/> for details. 《機械翻訳》運行している各バックエンドREPACKビュー内でのレポートの進行状況。 詳細は27.4.5を参照。 pg_stat_progress_repack

Repacking a partitioned table repacks each of its partitions. If an index is specified, each partition is repacked using the partition of that index. <command>REPACK</command> on a partitioned table cannot be executed inside a transaction block. 《機械翻訳》パーティション化されたテーブルを再パックすると、各パーティションが再パックされます。 インデックスが指定されている場合は、そのパーティションのパーティションを使用して各インデックスが再パックされます。 REPACKパーティション化されたテーブルでは、トランザクションブロック内で実行できません。

《機械翻訳》クラスタリングに関する注意。

<title>Notes on Clustering</title>

If the <literal>USING INDEX</literal> clause is specified, the rows in the table are physically rearranged according to the ordering implied by the specified index; this is known as <firstterm>clustering</firstterm>. This can have performance implications: in cases where you are accessing single rows randomly within a table, the actual order of the data in the table is unimportant. However, if you tend to access some data more than others, and there is an index that groups them together, you will benefit from using clustering. If you are requesting a range of indexed values from a table, or a single indexed value that has multiple matching rows, clustering will help because once the index identifies the table page for the first row that matches, all other rows that match are probably already on the same table page, and so you save disk accesses and speed up the query. 《機械翻訳》USING INDEX句が指定されている場合、そのテーブルの行は、指定された順序付けによって示されるインデックスに従って物理的に再配置されます。 これはクラスタリングと呼ばれます。 これはパフォーマンスに影響を与える可能性があります。 テーブル内で単一の行をランダムにアクセスしている場合、テーブル内のデータの実際のオーダーは重要ではありません。 ただし、一部のデータを他のよりも多くアクセスする傾向があり、それらをグループ化するインデックスがある場合は、クラスタリングを使用することでメリットが得られます。 テーブルからインデックス付けされた値のレンジを要求している場合、またはマルチプルマッチング行を持つ単一のインデックス付けされた値を要求している場合、クラスタリングはヘルプになります。 これは、インデックスが一致する最初の行のテーブルページを識別すると、マッチを持つ他のすべての行はおそらくすでに同じテーブルページにあるため、ディスクアクセスを節約し、問い合わせを高速化します。

For B-Tree indexes, the ordering used by clustering is the index's linear sort order. Other clusterable index access methods may use a different ordering strategy, one which may not necessarily correspond to any SQL sort order. If an index name is specified in the command, that index is used and is recorded as the table's clustering index. (This also applies to an index given to the <command>CLUSTER</command> command.) If no index name is specified, then the index that has been configured as the clustering one is used; if none has been configured, an error is thrown. An index can be set manually using <command>ALTER TABLE ... CLUSTER ON</command>, and reset with <command>ALTER TABLE ... SET WITHOUT CLUSTER</command>. 《機械翻訳》Bツリー索引の場合、クラスタリングで使用される順序付けは、そのインデックスのリニアソートオーダーです。 その他のクラスタリング可能インデックスアクセスメソッドでは、別の順序付けストラテジが使用される場合があります。 このは、SQLソートオーダーに対応しているとはかぎりません。 コマンドでインデックス名前が指定されている場合、そのインデックスが使用され、テーブルのクラスタリングインデックスとして記録されます。 CLUSTERコマンドに指定されたインデックスについても同様です。 インデックス名前が指定されていない場合は、クラスタリング対象として構成されているインデックスが使用されます。 構成されていない場合は、エラーがスローされます。 インデックスを手動で設定するには、ALTER TABLE ... CLUSTER ONを使用し、リセットをALTER TABLE ... SET WITHOUT CLUSTER.

Clustering is a one-time operation: when the table is subsequently updated, the changes are not clustered. That is, no attempt is made to store new or updated rows according to the clustering order. (If one wishes, one can periodically recluster by issuing the command again. Also, setting the table's <literal>fillfactor</literal> storage parameter to less than 100% can aid in preserving cluster ordering during updates, since updated rows are kept on the same page if enough space is available there.) 《機械翻訳》クラスタ化は1回限りのオペレーションです。 テーブルがその後更新された場合、その変更はクラスタ化されません。 つまり、クラスタ化されたオーダーに従って、新規または更新された行を格納しようとすることはありません。 (必要であれば、コマンドを再度発行することで定期的に再クラスタ化できます。 また、テーブルを設定するとfillfactorストレージパラメータをより小さい100%に設定すると、更新時にクラスタ順序付けを保護するのに役立ちます。 これは、十分なスペースが利用可能な場合、更新された行は同じページに保持されるためです。

When clustering on a B-Tree index, <command>REPACK</command> can rewrite the table using either an index scan on the specified index, or a sequential scan followed by sorting. It will attempt to choose the method that will be faster, based on planner cost parameters and available statistical information. When clustering on an index of an access method other than B-Tree, <command>REPACK</command> always uses an index scan. 《機械翻訳》B-ツリーインデックスでクラスタリングしている場合、REPACKは、指定したテーブルのインデックススキャン、またはインデックスの後にシーケンシャルスキャンを使用して並べ替えを書き換えることができます。 プランナコストパラメータおよび使用可能なメソッド情報に基づいて、より高速な統計の選択が試行されます。 B-ツリー以外のアクセス方式のインデックスでクラスタリングしている場合、REPACKは常にインデックススキャンを使用します。

Because the planner records statistics about the ordering of tables, it is advisable to specify the <literal>ANALYZE</literal> option, or to run <link linkend="sql-analyze"><command>ANALYZE</command></link> on the newly repacked table. Otherwise, the planner might make poor choices of query plans. 《機械翻訳》プランナはテーブルの統計処理に関する順序付けを記録しますので、ANALYZEオプションを指定するか、新しくパックし直したテーブルに対してANALYZEを実行することを推奨します。 さもないと、そのプランナは、問い合わせ計画の不適切な選択をmakeする可能性があります。

If no table name is specified in <command>REPACK USING INDEX</command>, all tables which have a clustering index defined and which the calling user has privileges for are processed. 《機械翻訳》REPACK USING INDEXでテーブル名前が指定されていない場合は、クラスタ化インデックスが定義されていて、コール側ユーザが権限を持っているすべての表が処理されます。

《機械翻訳》リソースに関するメモ。

<title>Notes on Resources</title>

<command>REPACK</command> creates a temporary copy of the table and all of its indexes, so you need free disk space at least equal to the sum of the table size and the index sizes. 《機械翻訳》REPACKでは、テーブルの一時的コピーとそのすべてのインデックスが作成されます。 このため、フリーディスクスペースは少なくとも等しいテーブルサイズの総和とインデックスのサイズが必要です。

If the <literal>USING INDEX</literal> clause is given and the planner chooses a sequential scan and sort to implement it, a temporary sort file of up to the size of the table is needed in addition to the above. This method is usually faster than an index scan, but if the disk space requirement is intolerable, you can disable this choice by temporarily setting <xref linkend="guc-enable-sort"/> to <literal>off</literal>; or omitting <literal>USING INDEX</literal> if the table doesn't need to be reordered. 《機械翻訳》USING INDEX句が指定され、プランナがそれを実装するシーケンシャルスキャンとソートを選択した場合は、上記に加えて、テーブルのサイズまでの一時的ソートファイルが必要です。 このメソッドは通常、インデックススキャンよりも高速ですが、ディスクスペースの条件が許容できない場合は、enable_sortを一時的にoff;に設定するか、テーブルの順序変更が必要ない場合はUSING INDEXを省略することで、この選択を無効にできます。

For the purposes of transaction ID wraparound (see <xref linkend="vacuum-for-wraparound"/>), <command>REPACK</command> is considered a single long-running transaction, which prevents <command>VACUUM</command> from cleaning up dead rows from other tables. It is advisable to monitor <structname>pg_stat_activity.backend_xid</structname> for the process running <command>REPACK</command> when repacking very large tables, to avoid causing excessive bloat in other tables. 《機械翻訳》トランザクションIDの周回（24.1.5を参照）において、REPACKは単一の長時間実行されるトランザクションとみなされ、これによりVACUUM他のテーブルの不要行の整理を防ぐことができます。 REPACK非常にラージなテーブルを再パックする場合、他のテーブルの過剰な膨張を防ぐために実行中のプロセスに対してモニタpg_stat_activity.backend_xidを使用することをお勧めします。

It is advisable to set <xref linkend="guc-maintenance-work-mem"/> to a reasonably large value (but not more than the amount of RAM you can dedicate to the <command>REPACK</command> operation) before repacking. 《機械翻訳》maintenance_work_memを適切なラージの値に設定することをお勧めします（ただし、REPACKオペレーションの前のリパックに使用できるRAMの量を超えないようにしてください）。

《機械翻訳》同時オペレーションに関する注意。

<title>Notes on Concurrent Operation</title>

警告

<command>REPACK</command> with the <literal>CONCURRENTLY</literal> option is not MVCC-safe. After the repacking transaction commits, the table will appear empty to concurrent transactions, if they are using a snapshot taken before repacking started. See <xref linkend="mvcc-caveats"/> for more details. 《機械翻訳》REPACKとCONCURRENTLYオプションはMVCC-セーフではありません。 トランザクションの再パッキングがコミットされた後、同時トランザクションがテーブルの再パッキングを開始したsnapshotを使用している場合、その前は同時トランザクションに対して空であるように見えます。 詳細は、13.6を参照してください。

<command>REPACK</command> copies the contents of the table (ignoring dead tuples) into a new file, sorted by the specified index, and also creates a new file for each index. It then swaps the old and new files for the table and all the indexes, and deletes the old files. Without the <literal>CONCURRENTLY</literal> option, an <literal>ACCESS EXCLUSIVE</literal> lock is acquired at the beginning and remains held throughout the operation to make sure that the old files do not change during the processing; otherwise, any concurrent changes would get lost due to the swap. 《機械翻訳》REPACKは、テーブル（無効タプルは無視）の内容を、指定したファイルでソートして新規インデックスにコピーし、さらにファイルごとに新規インデックスを作成します。 次に、テーブルおよびすべてのインデックスについて、古いファイルと新規ファイルを入れ替え、古いファイルを削除します。 CONCURRENTLYオプションを使用しない場合、ACCESS EXCLUSIVEロックは最初に取得され、オペレーションからmakeまで保持され、処理中に古いファイルが変更されないようにします。 そうしないと、スワップによって同時に行われた変更が失われます。

By contrast, when the <literal>CONCURRENTLY</literal> option is specified, the bulk of the operation is run with <literal>SHARE UPDATE EXCLUSIVE</literal> lock, and the <literal>ACCESS EXCLUSIVE</literal> lock is only acquired during the final phase to swap the table and index files. The data changes that took place during the creation of the new table and index files are captured using logical decoding (see <xref linkend="logicaldecoding"/>) and applied before the <literal>ACCESS EXCLUSIVE</literal> lock is requested. Once that lock is obtained, a final pass over any remaining captured concurrent data changes is done and the files are swapped. Thus the lock is typically held for a short time, depending on the amount of changes accumulated while the lock was being waited for. 《機械翻訳》対照的に、CONCURRENTLYオプションが指定された場合、オペレーションのバルクはSHARE UPDATE EXCLUSIVEロックとともに実行され、ACCESS EXCLUSIVEロックはテーブルおよびインデックスファイルをスワップする最終フェーズでのみ取得されます。 新しいテーブルおよびインデックスファイルの作成中に発生したデータの変更は、ロジカルデコーディング（第47章を参照）を使用して取得され、前に適用されますACCESS EXCLUSIVEロックが要求されます。 ロックが取得されると、取得された残りの同時データの変更に対する最終パスが実行され、ファイルがスワップされます。 したがって、ロックは通常、ロックが待機されている間に蓄積された変更の量に応じて、短時間保持されます。

Processing of these concurrent changes requires a fixed small amount of memory for each tuple concurrently updated or deleted, not limited by <xref linkend="guc-maintenance-work-mem"/>; if more than about 104 million rows are concurrently updated or deleted during the execution of <command>REPACK</command>, the command fails. In addition, the complete tuple data for all concurrent changes (except for TOAST columns that are not modified by <command>UPDATE</command>) are stored on disk separately. 《機械翻訳》これらの同時変更の処理には、同時に更新または削除される各メモリに対して固定された少量のタプルが必要であり、maintenance_work_memによって制限されません。 REPACKの実行中に約104,000,000行を超える行が同時に更新または削除されると、コマンドに障害が発生します。 さらに、すべての同時変更の完全なタプルデータ（UPDATEによって変更されないTOAST列を除く）は、ディスクに個別に格納されます。

<command>REPACK (CONCURRENTLY)</command> might fail to complete if DDL commands are executed on the table by other transactions during the repacking. 《機械翻訳》REPACK (CONCURRENTLY)再パック中に他のトランザクションがDDL上でテーブルコマンドを実行すると、が完了しない可能性があります。

<command>REPACK (CONCURRENTLY) USING INDEX</command> does not try to order the rows inserted into the table after the repacking started. 《機械翻訳》REPACK (CONCURRENTLY) USING INDEX再パックの開始後にトライに挿入された行は、オーダーからテーブルに移動されません。

The <literal>CONCURRENTLY</literal> option cannot be used in the following cases: 《機械翻訳》CONCURRENTLYオプションは、次の場合には使用できません。

  • The relation is not a table (e.g., it is a materialized view). 《機械翻訳》リレーションがテーブルではありません（マテリアライズドビューなど）。

  • The table is <literal>UNLOGGED</literal>. 《機械翻訳》テーブルはUNLOGGEDです。

  • The table is partitioned. 《機械翻訳》テーブルは仕切られている。

  • The table lacks a primary key and index-based replica identity. 《機械翻訳》このテーブルには、主キーやインデックスを拠点とするレプリカアイデンティティがありません。

  • The table is a system catalog or a <acronym>TOAST</acronym> table. 《機械翻訳》テーブルは、システムカタログまたはテーブルTOASTです。

  • The table's access method is not <literal>heap</literal>. 《機械翻訳》テーブルのアクセス方法はheap.NET以外ではありません。

  • The table is declared as a catalog table using the <link linkend="reloption-user-catalog-table"><literal>user_catalog_table</literal></link> storage parameter. 《機械翻訳》このテーブルは、user_catalog_tableカタログテーブルを使用してストレージパラメータとして宣言されています。

  • <command>REPACK</command> is executed inside a transaction block. 《機械翻訳》REPACKトランザクションブロック内で実行されます。

  • The <link linkend="guc-max-repack-replication-slots"><varname>max_repack_replication_slots</varname></link> configuration parameter does not allow for the creation of an additional replication slot. 《機械翻訳》max_repack_replication_slots設定パラメータでは、追加のレプリケーションスロットを作成できません。

例

<title>Examples</title>

Repack the table <literal>employees</literal>: 《機械翻訳》テーブルemployees:. 

REPACK employees;

Repack the table <literal>employees</literal> on the basis of its index <literal>employees_ind</literal> (since an index is specified, this is effectively clustering): 《機械翻訳》テーブルを再梱包しますemployeesインデックスに基づいてemployees_indインデックスが指定されているため、これは効果的にクラスタリングされます:。 

REPACK employees USING INDEX employees_ind;

Repack the <literal>employees</literal> table following the same index as was used before, in concurrent mode: 《機械翻訳》employeesテーブルは、前で使用されたのと同じインデックスに従い、モードと同時にを再梱包します。 

REPACK (CONCURRENTLY) employees USING INDEX;

Repack the table <literal>cases</literal> on physical ordering, running an <command>ANALYZE</command> on the given columns once repacking is done, showing informational messages: 《機械翻訳》テーブルを再梱包しますcases物理的順序付けでは、再梱包が完了すると、特定の列でANALYZEを実行し、情報メッセージを表示します。 

REPACK (ANALYZE, VERBOSE) cases (district, case_nr);

Repack all tables in the database on which you have the <literal>MAINTAIN</literal> privilege: 《機械翻訳》MAINTAINデータベース:.が存在する権限のすべてのテーブルを再梱包します。 

REPACK;

Repack all tables for which a clustering index has previously been configured on which you have the <literal>MAINTAIN</literal> privilege, showing informational messages: 《機械翻訳》MAINTAINインデックス。 次の情報メッセージが表示されています。 が存在し、以前にクラスタリング権限が構成された表をすべて再梱包します。 

REPACK (VERBOSE) USING INDEX;

互換性

<title>Compatibility</title>

There is no <command>REPACK</command> statement in the SQL standard. 《機械翻訳》ステートメント基準ではREPACK SQLはない。
